# 文字论坛实施计划书

日期：2026-10-20（北京时间）。

状态：需求方向已确认，以下具体规则与实施方案待用户确认。当前只生成计划，不实施数据库迁移、功能代码或部署。

依据：用户在本次聊天中提供的 AGENTS.md 指令、README-CONSTRAINTS.md、现有后端五层架构与已确认的论坛和站内提醒选项。

## 一、已确认需求

1. 论坛采用“主题帖 → 评论 → 评论下回复”的形式。
2. 帖子、评论、回复都支持点赞。
3. 第一版仅支持文字。
4. 收到他人的点赞、评论或回复后，提供站内提醒：打开网站时显示铃铛和未读数。
5. 复用游戏账号、登录会话、用户名和预设头像，让玩家直接参与讨论。

其中前三项及第四项的站内提醒范围为用户明确选择；评论的通知对象等具体规则和第五项账号接入方案随本计划确认。

## 二、技术选型声明与最高优先级建议

| 层次 | 技术与实施方式 |
| --- | --- |
| 前端 | 沿用 HTML、CSS、原生 JavaScript，扩展 forum.html，新增论坛详情页及共享客户端 |
| 后端 | 沿用 Python + FastAPI，按 Controller → Service → Repository 分层 |
| 数据访问 | 沿用 SQLAlchemy / PyMySQL，所有同步认证和数据库访问通过现有有界执行器 |
| 数据存储 | 沿用 MySQL / InnoDB，兼容项目当前 MySQL 5.7 约束，不依赖窗口函数或 CHECK 执行效果 |
| 数据库迁移 | 新增 Flyway V4，保留已执行的 V1～V3 |
| 部署 | 沿用 Nginx、单 Uvicorn 进程、现有连接池和资源边界 |

**最高优先级建议：先固定回复归属、点赞幂等及通知接收规则，再实现交互界面。** 回复必须属于同一帖子及同一条顶层评论；同一账号对同一内容最多保留一个赞，网络重试不会多点赞、重复发帖、重复回复或重复提醒。互动和通知在同一事务中保存。

论坛数据永久保存在数据库，按需分页获取。沿用项目已有的海岛背景、深蓝面板和暖金配色，适配手机。

## 三、建议默认规则：随计划一并确认

### 1. 访问与发布

- 游客可以浏览帖子、评论和回复；发帖、评论、回复、点赞、取消点赞需要登录。
- 作者身份由服务端 Cookie 会话决定，请求体不能指定作者账号。
- 展示作者当前用户名和当前头像，与已有游戏账号一致。
- 标题 1～80 个 Unicode 码点，正文 1～2000 个，评论及回复 1～500 个；去除首尾空白后不可为空。前后端采用一致计数方式。
- 文字按纯文本展示，保留换行；输入中的 HTML 作为文字显示，不作为页面执行。
- 每次发帖、评论或回复生成 request_id；失败重试沿用原编号和原负载。同账号同编号同负载返回原内容，编号重复但负载不同返回 409。
- 初始频率建议：同账号发帖间隔 60 秒，评论和回复共用 3 秒间隔，参数可配置；幂等重试不重复占用发布次数，过于频繁返回 429 及重试时间。

### 2. 评论与回复

- 帖子下展示顶层评论；每条顶层评论下展开回复列表。
- 可以回复顶层评论，也可以回复已有回复；后者显示“某某回复某某”，统一归入原顶层评论，界面保持两层。
- 后端检查帖子、根评论、回复对象存在且归属一致，拒绝跨帖或跨评论串关联。
- 发布后显示服务端确认的内容，网络失败时保留输入和重试入口。

### 3. 点赞

- 帖子、顶层评论和回复各自有独立点赞数与“我已点赞”状态。
- 再次点击已点赞按钮可以取消；第一版允许给自己的内容点赞。
- 接口采用明确的 PUT 点赞 / DELETE 取消点赞，不使用每调用一次就翻转状态的接口。
- 服务端事务配合唯一约束维护点赞记录和计数：重复 PUT 不重复增加，重复 DELETE 不继续扣减。
- 同一内容请求期间禁用对应点赞按钮，完成后使用服务端返回的计数和状态；失败保留原展示并提示重试。

### 4. 列表与边界

- 帖子按发布时间倒序，顶层评论和回复按发布时间正序，使用 ID 作为稳定排序的补充。
- 帖子、顶层评论每批 20 条，回复展开后每批 10 条；接口单批最多 50 条，采用游标及“加载更多”。
- 列表只返回正文摘要；详情才返回完整正文，回复按需展开，不一次拉取整个论坛。
- 包含加载、空列表、发布成功、失败、重试和会话过期反馈。
- 换号或退出后清空发布状态及“我已点赞”状态，晚到的旧账号响应不得覆盖新账号界面；已公开的讨论内容仍可浏览。
- 当前实施范围为发帖、评论、回复、点赞、取消点赞及站内消息提醒。编辑删除、管理员后台、举报、搜索、分类、图片、私信和关闭网站后的浏览器推送不在本次实现范围；如需要其中功能，应在确认计划前调整范围。

### 5. 站内消息提醒

| 互动 | 接收人 | 示例 |
| --- | --- | --- |
| 点赞帖子 | 帖子作者 | 小明赞了你的帖子《扫雷心得》 |
| 点赞评论或回复 | 该评论或回复的作者 | 小明赞了你的评论 |
| 发表顶层评论 | 帖子作者 | 小明评论了你的帖子《扫雷心得》 |
| 回复评论或已有回复 | 直接被回复内容的作者 | 小明回复了你：“这个方法不错” |

- 自己与自己的内容互动不产生通知。回复默认只提醒直接被回复的人，不额外通知整串参与者或帖子作者。
- 同一次发布重试不产生重复通知；同一账号对同一内容首次点赞时产生一条通知，后续取消或重新点赞不追加通知，也不重置已读状态。首次点赞的提醒保留为历史互动记录。
- 通知记录保存在服务端；离线时正常积累，下一次登录或回到网站后可读取，跨浏览器保持已读状态。
- 铃铛显示未读数量，超过 99 显示“99+”。点击铃铛展示按时间倒序的消息列表，每批 20 条，包含互动者、类型、内容摘要、时间及未读标识。
- 仅打开消息面板不自动全部已读；点击某条通知标记该条已读并跳转对应内容，也提供“全部已读”。列表和已读接口只操作当前账号自己的通知。
- “全部已读”使用此次查询返回的最大通知 ID 作为边界，只处理该边界之前的通知，保留并发到达的新通知为未读。
- 帖子通知跳转帖子；评论和回复通知使用评论编号定位，并加载目标与根评论上下文，避免用户连续翻页寻找目标。目标不可用时显示提示并提供返回帖子或论坛入口。
- 第一版仅提供站内铃铛和列表，不请求浏览器系统通知权限。

## 四、页面与交互

### forum.html：论坛列表

- 保留当前顶部“排行榜 / 无职游戏 / 论坛”导航及账号入口。
- 标题区域提供“发表主题”入口，登录后打开标题、正文表单；未登录先打开现有登录弹窗。
- 帖子卡片展示标题、正文摘要、作者头像及用户名、时间、评论数和点赞数。
- 卡片标题进入可收藏的详情地址；点赞按钮独立操作，不触发详情跳转。
- 列表底部“加载更多”，重新进入论坛恢复合理的返回位置。

### forum-post.html?id=帖子编号：帖子详情

- 显示帖子完整内容、作者、发布时间、帖子点赞入口和返回论坛入口。
- 顶层评论各自显示作者、文字、时间、点赞和回复按钮。
- “回复”明确标识目标，提交前可以取消；根评论下用“查看回复 / 加载更多回复”展开。
- 所有交互使用标准按钮、链接及有标签的输入框；键盘可完成发布与回复操作，弹窗关闭后恢复焦点。
- 页面刷新及直接访问详情地址能够独立读取；无效编号、已不存在的帖子提供清晰状态及返回入口。

### 全站铃铛与消息面板

- 首页、排行榜、论坛列表、帖子详情和其他共用账号入口的页面，统一接入站内消息组件。
- 游戏进行中在顶部提供消息入口，新消息更新未读数；玩家主动点击后查看消息。跳转讨论沿用现有棋局保存机制，回到游戏仍能续玩。
- 未登录时隐藏私人消息列表和轮询；登录后读取未读数。退出或换号后立即清空旧列表、未读数和未完成请求的渲染资格。
- 消息面板支持键盘操作、关闭后焦点恢复，以及加载、空消息、错误和重试状态。未读数通过可访问标签说明，避免每次轮询播报整份列表。

## 五、数据库设计

新增五张表，关联已有 users，不改造账号或游戏成绩表。

| 表 | 核心字段与作用 |
| --- | --- |
| forum_posts | id、user_id、request_id、title、body、like_count、comment_count、created_at |
| forum_comments | id、post_id、user_id、request_id、root_comment_id、reply_to_comment_id、body、like_count、reply_count、created_at |
| forum_post_likes | post_id、user_id、created_at；联合主键限制一个账号对一个帖子只赞一次 |
| forum_comment_likes | comment_id、user_id、created_at；顶层评论和回复共用点赞表 |
| forum_notifications | id、recipient_id、actor_id、kind、post_id、comment_id、event_key、read_at、created_at；保存接收人的站内消息 |

- 主键及外键类型与现有 users.id、BIGINT UNSIGNED 约定一致，文字使用 utf8mb4，时间由服务端按 UTC 记录。
- 帖子和评论分别建立 `(user_id, request_id)` 唯一键，用于创建请求的幂等确认；重复编号时比较已保存内容。
- 顶层评论的 root_comment_id 和 reply_to_comment_id 均为空；回复保存其顶层评论编号和直接回复对象编号。
- 建立用户、帖子和评论之间的外键；根评论与回复对象的同帖、同串校验由业务层完成。
- 帖子列表按 id 倒序分页；评论索引 `(post_id, root_comment_id, id)`，回复索引 `(root_comment_id, id)`，作者发布频率查询使用 `(user_id, created_at, id)`。
- 帖子的 comment_count 包含顶层评论及回复；根评论的 reply_count 仅统计其串下回复；计数增加、点赞增减和内容创建在同一事务提交。
- 统一写事务锁顺序为用户 → 帖子 → 评论；先确认幂等状态，再检查发布间隔，再写数据。异常时整体回滚。
- 查询采用有限页和批量关联当前作者、头像及当前账号点赞状态，避免每条内容各自请求作者或执行 SQL。
- 通知关联接收人、互动者、帖子和可选评论；通知类型与关联字段由业务校验。读取时关联当前用户名、头像和有限文字摘要，使用纯文本展示。
- 通知唯一键 `(recipient_id, event_key)`：点赞事件按“对象类别、对象 ID、点赞人”生成固定键；评论和回复事件按新评论 ID 生成固定键，防止重试或重复点赞重复通知。
- 通知索引 `(recipient_id, id)` 用于倒序分页，`(recipient_id, read_at, id)` 用于未读查询和已读更新。未读数量查询可在 100 条时截断，与“99+”展示保持一致，避免扫描无限数量的未读记录。
- 内容或点赞写入、对应计数变化与通知生成在同一事务中完成；通知写入失败时整个互动回滚，重试仍使用原幂等规则。

## 六、接口设计

所有接口位于 `/api/forum/`；写请求沿用项目现有同源校验及 HttpOnly Cookie，会话认证与论坛事务在同一个数据库工作线程内完成。

| 方法与路径 | 行为 |
| --- | --- |
| GET /posts | 分页读取帖子摘要、计数及可选当前用户点赞状态 |
| POST /posts | 登录后创建文字帖子，接收 request_id、title、body |
| GET /posts/{post_id} | 读取帖子正文、作者和计数 |
| GET /posts/{post_id}/comments | 分页读取顶层评论 |
| POST /posts/{post_id}/comments | 创建顶层评论，或通过 reply_to_comment_id 回复同帖内容 |
| GET /comments/{comment_id}/replies | 分页读取指定顶层评论下的回复 |
| GET /posts/{post_id}/comments/{comment_id} | 读取指定评论或回复及根评论上下文，用于通知定位；校验同帖归属 |
| PUT /posts/{post_id}/like | 幂等地为帖子点赞 |
| DELETE /posts/{post_id}/like | 幂等地取消帖子点赞 |
| PUT /comments/{comment_id}/like | 幂等地为评论或回复点赞 |
| DELETE /comments/{comment_id}/like | 幂等地取消评论或回复点赞 |
| GET /notifications/unread-count | 登录后读取自己的未读数，最多返回 100，对应界面“99+”；附最新通知 ID |
| GET /notifications | 登录后分页读取自己的消息列表及本次查询的通知 ID 边界 |
| PUT /notifications/{notification_id}/read | 幂等标记自己的单条通知已读 |
| POST /notifications/read-all | 按 through_id 边界将自己的已有通知标记为已读，保留之后到达的新通知 |

公开读取在有效会话存在时返回 liked_by_me，无有效会话时按游客返回。写操作未登录返回 401；对象不存在返回 404；关联或幂等负载冲突返回 409；输入无效返回 422；频率超限返回 429；执行器或数据库繁忙沿用 503。

## 七、请求体与资源边界

已检查到 Nginx 当前 `/api/` 限制为 4KB，现有应用请求体中间件仅覆盖登录、头像和挑战写入。论坛较长中文正文需要单独配置。

- 为 `/api/forum/` 设置独立 32KiB 请求体上限，Nginx 与应用中间件保持一致；该额度容纳文字上限及 JSON 转义开销，字段字符限制仍独立执行。
- 应用在 JSON 解析前按实际接收字节计数，包括没有 Content-Length 的分块请求。
- 登录、头像、挑战维持既有上限，避免把论坛额度扩大到其他写接口。
- 分别更新本机 Docker 和宝塔部署模板；本次确认计划不修改线上配置。
- 复用现有四个数据库执行槽、有限连接池及单 Uvicorn 进程，不新增常驻服务。
- 不通过逐秒轮询更新帖子和点赞；随页面进入、用户加载及写入成功刷新相关内容。
- 站内消息在登录、进入页面和页面重新可见时查询未读数；登录且页面可见期间每 60 秒轻量查询一次，前一次请求结束后再安排下一次，隐藏页面及退出后停止。可见性切换查询设置冷却，避免频繁切换造成密集请求。
- 用户主动打开铃铛时读取消息列表；全站同一页面只初始化一个消息控制器，消息失败不阻断游戏和论坛操作，过载时遵循 503 与 Retry-After 退避。
- 真实服务器容量以目标环境实测为准，不根据本机或 SQLite 回归估算在线人数。

## 九、验收标准

| 类别 | 必须验证 |
| --- | --- |
| 身份与访问 | 游客可读、未登录不可写、伪造作者无效、跨站写入被拒绝 |
| 帖子与文字 | 中文、换行、长度边界、空白内容、HTML 文字安全显示、发布失败保留输入 |
| 评论与回复 | 顶层评论、回复评论、回复已有回复、跨帖/跨评论串引用被拒绝 |
| 幂等 | 同请求重试仅创建一条内容，重复编号修改负载被拒绝，重试不被发布间隔误拦 |
| 点赞 | 三种内容均可点赞/取消；重复、快速及并发请求不产生重复记录或负计数；刷新保持状态 |
| 消息生成 | 点赞、评论和回复提醒正确接收人；自己互动不通知；重复请求及反复点赞不刷消息；互动和通知一起提交或回滚 |
| 消息隐私与已读 | 只读写自己的通知，换号不残留；刷新及跨浏览器保持已读；全部已读不吞掉边界之后的新消息 |
| 消息定位 | 点击帖子/评论/回复消息可打开目标；目标在后续分页时仍能定位，缺失目标有返回入口 |
| 消息资源 | 登录且可见时才检查未读数；隐藏、退出时停止；每次请求完成后安排后续检查；失败退避，不阻断现有页面 |
| 事务与分页 | 异常整体回滚；计数与记录一致；有限页及游标加载，无逐项查询作者的问题 |
| 会话切换 | 退出/换号立即更新个人点赞及发布状态，旧响应不能恢复旧账号状态 |
| 请求体 | 中文正文可正常提交；超过论坛上限的普通及分块请求被拒绝；登录等原有上限不变 |
| 页面 | 桌面、375px 和 320px 手机宽度，无页面横向溢出；键盘发布、回复、点赞可用 |
| 现有功能 | 登录、头像、三个独立游戏与三个分榜相关回归通过 |
| MySQL / Flyway | 专用测试库执行 V4、再次迁移无待执行项，并验证真实外键、唯一键及并发写入；条件不足时明确记录待验收 |

测试输出写入日志；对话只报告失败摘要或最终统计。只运行受改动影响的检查，发现新问题或改动后再针对性补测，不重复粘贴完整 RED/GREEN 日志。
