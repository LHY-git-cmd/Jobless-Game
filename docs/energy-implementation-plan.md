# 账号体力机制与首页记录面板调整计划书

日期：2026-10-22（北京时间）。状态：用户已确认并授权执行；本地实现及专项验收完成，结果见实施报告。

## 1. 已确认需求

用户要求新增账号体力，在头像右侧区域显示，并删除截图中的首页“我的通关记录”面板。已进一步确认：每30分钟恢复1点，上限5点；重新开始不退还旧局消耗，并再扣1点开启新局；覆盖扫雷、照明、数独普通关卡，入门免费。

“删除通关记录”按截图移除首页该展示面板及其装配，不清空账号的星星、经验、等级、关卡进度或排行榜数据。

## 2. 体力规则与边界

| 场景 | 体力变化及行为 |
| --- | --- |
| 新老账号首次使用本机制 | 统一初始5点，账号共用，上限5点 |
| 浏览选关、查看规则、取消开始确认 | 不扣体力 |
| 正式开始普通新局 | 服务端成功创建尝试时扣1点 |
| 同一局继续、刷新、跨页恢复 | 不重复扣体力 |
| 当前普通棋局成功通关 | 返还本次开局消耗的1点；同一局只返一次，最多恢复到5点 |
| 重玩已通过的普通关 | 新局仍扣1点，该次通关仍返1点；星星和经验沿用已有幂等规则 |
| 重新开始 | 旧局消耗不退，新局另扣1点；体力不足时不放弃旧局，不清空原棋盘 |
| 失败、主动放弃或尝试过期 | 不退还消耗；能够继续的原活动棋局仍可继续 |
| 入门教学 | 免费，不扣体力，也不通过免费教学额外增加体力 |
| 体力为0 | 禁止创建或重开普通新局，仍可继续已扣体力的活动局、学习入门或等待恢复 |
| 自然恢复 | 从体力首次低于上限开始，每30分钟恢复1点；跨页、离线、退出登录期间正常累计 |
| 已满体力 | 停止累计恢复进度；再次消耗后重新开始30分钟周期 |
| 未满时继续消耗或通关返还 | 保留当前恢复周期；返还达到5点时清除剩余周期 |
| 升级前已存在的棋局 | 不追扣，也不返还未支付的体力；历史成果保留 |

自然恢复使用服务器真实时间，与关卡暂停计时相互独立。PK不在本次普通关卡机制范围内，不调整竞速规则。普通旧版本棋局通过同一正式尝试接口创建时也需要扣体力，不能借旧关卡入口绕过限制。

示例：5点开局后剩4点；通关恢复5点。5点开局后剩4点，此时重开再扣1点，剩3点，新局通关后剩4点（未计自然恢复）。如果开局后已自然恢复至5点，通关返还仍保持5点。

## 3. 技术选型声明

沿用现有原生HTML/CSS/JavaScript、FastAPI、SQLAlchemy、MySQL及Flyway，不增加框架、Redis、定时任务或常驻服务。继续满足2核2GB及有界数据库连接要求。

**最高优先级建议：体力扣返与重开必须由服务端事务统一完成，尤其不能在体力不足时先放弃旧局。** 浏览器只展示和提交操作意图，不能提交自己的体力、恢复时间或返还数量。

当前后端已有每账号事务锁、正式尝试、幂等创建和不可变通关快照，可复用这些能力。新增账号体力状态及每次付费尝试的扣返凭证，防止并发扣成负数、断网重试重复扣费、重复通关重复返还。凭证随可清理的尝试级联回收，不创建无限增长的永久体力流水。

恢复采用按服务器时间计算并在读取或操作时结算，无需后台每30分钟扫描。开始、通关及读取返回带修订号的权威体力；客户端拒绝旧响应覆盖新值，换号后废弃旧请求与倒计时。

## 4. 后端与数据库方案

1. 新增体力状态表及尝试扣返凭证表；用新增Flyway V15发布，若实施时版本号已占用则顺延。不修改已执行迁移或历史题库。
2. 新增当前账号体力只读资源，返回当前值、上限、恢复间隔、下一点恢复时间及修订号。自然恢复、扣除和返还均由后端校准。
3. 正式开局在同一事务内核对可用体力、创建尝试并扣1点。请求原键重试不再扣；已有活动局恢复不扣。
4. 新增原子的重开资源：检查归属、当前状态、体力和幂等键后，在同一事务内结束旧局并创建新局。失败全回滚，原棋局可继续。
5. 合法通关在现有结算事务中返还1点，并返回体力快照；重复PUT或查询历史结果不重复返还。入门及升级前未付体力的尝试不返还。
6. 三款游戏共用账号体力，多标签页和多游戏并发也由同一账号锁串行保证余额。

## 5. 页面与操作方案

- 在截图头像右侧增加体力图标和“5 / 5”，未满时显示下一点恢复倒计时。颜色沿用现有深蓝、暖金及账号状态风格，图标使用SVG。
- 首次读取、开始、通关、重开和页面重新可见时同步权威体力。倒计时在本地显示，仅在恢复节点重新核对服务器，不进行每秒请求。
- 普通开始确认说明消耗1点、通关返1点；重开说明原消耗不返并再消耗1点。体力不足时明确提示恢复时间，保持原棋局和已有输入。
- 三款游戏的开局、通关和重开立即更新体力显示，体力更新不等待星星动画完成。已读取的旧结算快照不能覆盖更晚的体力。
- 首页删除“我的通关记录”整个面板及其初始化，保留介绍、三个游戏入口和顶部账号区域；移除面板后检查桌面及手机排版。
- 不因移除首页面板删除其他页面仍可使用的历史记录能力或后端数据。

## 6. 实施顺序、TDD与提交

用户确认本计划后执行：

1. **体力规则与持久化**：先写初始值、30分钟边界、离线多次恢复、满体力重置周期、并发扣除及幂等扣返测试，观察失败后实现模型、服务和V15迁移。
2. **正式游戏流程**：先测三款游戏普通扣返、入门免费、继续不扣、通关重放、零体力、重开事务回滚、重复开关、账号隔离及旧尝试兼容，再实现原子重开和接口快照。
3. **界面与首页**：先测体力状态的账号隔离、旧修订拒绝及开始/通关同步，再接入三款会话、头像旁体力与倒计时，移除首页面板。
4. **验收**：运行受影响的前后端回归；在独立Chrome验证普通扣返、入门免费、重开不退、体力不足、倒计时、刷新及换号、首页面板删除、320/375px布局；使用临时MySQL/Flyway验证真实迁移及并发事务。
5. **交付**：更新目录树、说明和实施报告，按功能用中文提交。所有日志落文件，只读取失败摘要及最终统计；不重复运行无变化且已通过的相同测试。

本次不执行生产部署或业务数据库迁移。本地预览需更新代码及测试库后才能体验；若旧端口进程重启仍被自动审批阻止，将提供新的独立预览地址，不擅自结束该进程。
