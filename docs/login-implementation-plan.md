# 登录功能实施计划书

日期：2026-10-18

状态：已加入 2 核、2GB 内存及宝塔面板共存约束，等待用户确认计划后实施。

## 一、已确认需求

1. 后端使用 Python + FastAPI，数据库使用 MySQL，建表与后续结构变更使用 Flyway。
2. 游戏入口页、排行榜页、论坛页的右上角提供“登录”按钮。
3. 未登录时，点击任一关卡入口先打开登录弹窗；登录成功后继续进入所选关卡。通过右上角按钮登录时，成功后停留在当前页面。
4. 弹窗采用液态玻璃透明效果：半透明背景、背景模糊、柔和高光边缘，沿用海岛页面的深蓝与暖金色。
5. 表单包含用户名、密码。说明“用户名不存在时自动创建账号”，提交按钮为“登录并继续”。
6. 用户名不存在时自动注册并登录；已存在时必须验证原密码，密码错误不得创建另一个同名账号或修改原密码。
7. 用户名唯一，英文大小写视为相同；允许汉字、英文字母和数字混合，不允许空白、标点或表情符号。
8. 用户名长度：汉字计 1.5、ASCII 英文字母和数字计 1，总计不超过 12，且不能为空。
9. 密码至少 6 个字符；保留密码原始内容，不自动去除空格，不改变大小写。
10. 服务器只有 2 核、2GB 内存，同时运行宝塔面板与其他必要配置。本项目与系统、面板和现有服务共享资源，部署设计必须保留内存余量。

## 二、技术选型声明与三条关键改进建议

采用现有原生 HTML/CSS/JavaScript 前端，新增 FastAPI API、SQLAlchemy 数据访问与 PyMySQL 驱动。生产环境复用宝塔已有 Nginx/MySQL（如已安装），Python 使用一个 Uvicorn 工作进程。Flyway 使用独立命令行运行 SQL 迁移，不由 ORM 自动建表。

1. **约束常驻资源。** Python 单工作进程，数据库小连接池；复用现有 Web 与数据库服务。页面与游戏素材由 Nginx 提供，游戏逻辑继续在浏览器执行。按照服务器实际可用内存确定最终配置。
2. **限制登录计算并保持账号安全。** 前后端统一校验，数据库唯一索引保证重名处理；Argon2id 显式配置并限制同时计算数量。数据库保存密码哈希，Cookie 保存随机会话凭据，前端不保存密码。登录入口同时设置可配置的频率限制，防止突发登录或自动注册持续占用两核 CPU。
3. **发布阶段执行迁移。** Flyway 在发布维护窗口单次执行并退出。本地由 FastAPI 同时提供页面与 API，生产由 Nginx 将 `/api/` 转发给 FastAPI，三个页面均使用同源相对地址。Flyway 已执行迁移后续以新增文件调整。

## 三、数据与接口设计

### 用户表 `users`

前后端按 Unicode 字符采用相同规则：汉字计 3、ASCII 字母数字计 2，上限 24，避免小数计算。保存用户最初的显示名，另存英文转小写的账号键；并发首次登录必须遵守唯一约束。

- `id`：主键。
- `username`：首次注册的显示名。
- `username_key`：英文转小写后的账号键，采用能保持其他字符差异的排序规则，并设置唯一索引。
- `password_hash`：带算法参数及盐值的密码哈希。
- `created_at`：创建时间，统一使用 UTC。

### 会话表 `auth_sessions`

- `id`：主键。
- `user_id`：关联用户。
- `token_hash`：随机会话凭据摘要，唯一。
- `created_at`、`expires_at`：UTC 创建与到期时间。
- 会话有效期默认 7 天，可通过配置调整。

数据库连接地址、数据库名、账号及密码使用环境变量配置。提供不含真实凭据的示例配置。迁移仅针对配置的项目数据库执行。

密码使用 Argon2id 哈希。会话 Cookie 设置 HttpOnly、SameSite，正式 HTTPS 环境启用 Secure；数据库只保存随机会话凭据的摘要与到期时间。

### API

| 方法与路径 | 行为 |
| --- | --- |
| `POST /api/auth/login` | 校验输入；首次自动注册或验证已有密码；创建会话并设置 Cookie |
| `GET /api/auth/me` | 查询当前有效会话与显示名，供刷新页面和跨页导航恢复登录状态 |
| `POST /api/auth/logout` | 注销当前会话并清除 Cookie |

修改登录状态的接口校验同源请求。错误响应不包含密码、密码哈希或数据库内部信息。

## 四、前端交互设计

- 三页复用一个登录模块和弹窗样式，避免重复实现校验与会话处理。
- 顶部保留“排行榜 / 无职游戏 / 论坛”顺序，在右侧放登录入口；窄屏分行，避免挤压导航。
- 登录后右上角显示用户名，并提供退出登录入口。
- 点击关卡时记录目标关卡；取消弹窗后保持在入口页，不开始计时；登录成功后再显示原有规则弹窗。
- 输入框有明确标签、用户名计数、密码长度提示；错误提示位于对应输入框附近。
- 提交期间显示等待状态，防止重复提交；请求失败后保留用户名，允许重试，不伪造登录成功。
- 支持关闭按钮、Escape、Tab 焦点限制与关闭后焦点恢复；允许粘贴和密码管理器填写。
- 透明效果不可用时提供可读的背景色；手机键盘弹出后表单仍可滚动访问。

## 六、2 核、2GB 与宝塔共存的资源设计

### 部署结构

浏览器加载游戏并执行棋盘逻辑 → 宝塔现有 Nginx 提供静态页面与资源，转发 `/api/` → 一个 Uvicorn 工作进程 → 项目 MySQL 数据库。

生产默认使用现有 Linux/宝塔服务管理能力和项目 Python 虚拟环境。登录与会话使用 MySQL，不增加 Redis、Celery 或其他常驻业务服务。本地静态服务器仍可预览页面，真实登录需连接后端。

### 初始参数

| 项目 | 初始设计 | 调整依据 |
| --- | --- | --- |
| Python 工作进程 | `--workers 1`，关闭开发热重载 | 按实测内存与接口延迟决定是否调整，不套用按 CPU 核数自动扩进程公式 |
| API 并发保护 | Uvicorn `--limit-concurrency 32` 起步 | 此值是进程并发连接/任务保护阈值，超限返回 503，不代表在线人数或吞吐承诺 |
| 数据库连接池 | `pool_size=3`、`max_overflow=0`、`pool_timeout=3` 秒 | 应用连接总数有界；数据库超时转换为可重试响应 |
| MySQL 缓存 | `innodb_buffer_pool_size=256M` 作为评估起点 | 不启用专用数据库服务器的自动内存占用方案；缓存之外还存在其他 MySQL 内存开销 |
| MySQL 连接数 | 项目单独实例可评估 `max_connections=20` | 如数据库被现有服务共用，先清点其他连接需求，项目仅限制自身连接池，不直接降低共享实例全局上限 |
| 密码哈希 | Argon2id：`memory_cost=65536` KiB、`time_cost=3`、`parallelism=1` 起步 | 单次计算内存约 64MiB，参数显式设置；目标服务器实测耗时后调整 |
| 登录计算并发 | 每个进程最多 1 个登录计算流程，无无界等待队列 | 哈希和同步数据库访问通过受限线程执行，避免阻塞事件循环；繁忙时返回 429 与重试提示 |
| 登录频率 | Nginx 登录路径按 IP 初始 `5r/m`、`burst=5`，可配置 | 测试共享出口及正常用户重试场景；仅信任本机反向代理转发的客户端地址 |
| 登录请求体 | 最大 4KiB | 请求进入密码计算前检查，超限返回 413；与密码最少 6 字符规则兼容 |
| 过期会话清理 | 使用现有计划任务定期分批删除，使用到期时间索引 | 控制每批数量，避免整表扫描和一次大事务；不增加清理常驻进程 |

密码校验与新用户哈希、自动重哈希均受同一个并发保护约束。普通会话查询不触发密码哈希。前端仅在页面初始化及必要操作时验证会话，不进行每秒轮询；游戏计时器也不向服务器逐秒提交。

### 内存预算与发布峰值

下面是设计目标，尚非实测占用，不能作为进程内存上限或可承载人数保证。先读取目标机器实际内存、本底服务占用和可用内存，再调整；2GB 的实际可用容量以操作系统报告为准。

| 部分 | 初步预算目标 |
| --- | --- |
| 系统、宝塔及现有必要服务，不重复计入下列服务 | 400–650MiB，需先实测 |
| MySQL 全进程 | 450–600MiB，含缓存及其他开销，需按版本实测 |
| Python 全进程及受限密码计算 | 200–300MiB，需实测 |
| Nginx | 20–50MiB，需实测 |
| 运行余量 | 尽量保留至少 350MiB 可用内存 |

如果宝塔或现有服务的本底占用超过预算，先重新分配资源，再决定上线参数，不以本机开发环境运行成功推断目标服务器一定可运行。

Flyway 在发布维护窗口执行，必要时先停止 Python 应用腾出内存；迁移完成后退出再启动应用。JVM 初始可评估 `-Xms32m -Xmx256m`，堆内存上限不等于 Flyway 总进程内存，需测量总峰值。依赖构建和资源处理优先在开发/构建机器完成。

### 验收与容量边界

- 记录服务启动前的 `MemAvailable`、系统与面板本底占用，以及启动后的进程内存、CPU、MySQL 连接数。
- 在目标规格环境逐级增加登录请求并发，例如 1、2、5、10，验证过载请求被有界拒绝，实际哈希并发始终不超过 1。
- 记录目标机登录请求的 p50/p95、实际吞吐、429/503 比例和内存峰值；过载期间普通会话查询仍能在设置的超时内响应。
- 稳定性检查包括：无 OOM、无持续换页抖动、运行后内存不随请求数量持续增长、会话清理任务可分批完成、磁盘日志有轮转。
- 如无法访问目标规格环境，报告明确标记容量与资源验收待完成，不用桌面机器的结果承诺生产承载量。
- 画面透明与背景模糊在浏览器端渲染，不增加服务器的实时图形计算任务。最终在线承载量还取决于带宽、素材缓存命中率和登录频率。
