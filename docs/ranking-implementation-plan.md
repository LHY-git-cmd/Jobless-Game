# 排行榜与通关记录实施计划书

日期：2026-10-18

状态：用户已于 2026-10-18 明确要求“开始执行计划”。数据库迁移文件、接口、逐关流程、开发验收按钮及四个榜单页面已实施；真实 MySQL/Flyway 和目标服务器验收待配置。实际产出与验证结果见 [实施报告](./ranking-implementation-report.md)。本文遵循根目录 README、README-CONSTRAINTS.md、后端五层架构及用户最新提供的 AGENTS.md 流程。

## 一、已确认需求

1. 排行榜主页展示玩家用户名和完整三关通关总时长，按用时从小到大排名。
2. 三个分页面分别展示扫雷、照明、数独的单游戏时长排行。
3. 总榜必须取同一轮按扫雷、照明、数独顺序全部通关的成绩，不能组合不同轮次的单项最好成绩。
4. 总榜每个玩家使用自己最好一轮的总时长参榜。
5. 每个玩家的每个游戏，以及完整三关的一轮成绩，都分别保留最佳记录和最近三次记录。
6. 最佳记录若已在最近三次之内，只保存一次；每人每类最多四条已完成记录，四类合计最多十六条。
7. 使用现有账号和登录会话。新增表关联 users.id，排行榜显示 users.username。
8. 技术沿用原生 HTML/CSS/JavaScript、Python + FastAPI、MySQL、Flyway，保持 Controller → Service → Repository 的调用方向。
9. 服务器为 2 核、2GB，需与宝塔等服务共存，复用现有单 Uvicorn 进程、连接池和有界数据库执行器。
10. 游戏流程改为每轮只能从第一关扫雷开始；本轮通关扫雷后才能进入照明，通关照明后才能进入数独。历史通关成绩不能解锁新一轮的后续关卡。
11. 开发测试阶段提供临时“一键通关”按钮，只完成当前关；该关成功保存后，由玩家按正常流程进入下一关，不一次完成整轮三关。按钮用于快速验收，后续移除。

## 二、本计划提出的默认规则

以下细节属于本次方案建议，随计划书一并确认；并非用户已经逐项确认的需求。

- **单游戏参榜资格**：按本轮顺序解锁并通关该游戏即可进入对应单游戏榜；完整通关三关的资格要求用于总榜。单游戏榜的存在不代表允许从游戏首页直接挑战第二或第三关。
- **并列规则**：整数秒相同时并列，采用 1、1、3 的竞赛排名；同分展示顺序按该成绩达成时间、用户 ID 升序，翻页后保持同一计算口径。
- **最佳记录替换**：只有严格更快才替换最佳；同秒的新成绩进入最近三次，原最佳的达成时间保持不变。
- **最近三次**：按服务端成功接收通关成绩的 UTC 时间及记录 ID 倒序判定，不按用时选取，不信任客户端上传的日期。
- **计时口径**：继续使用首次有效操作起计时、整数秒冻结与合计的既有规则；规则阅读、关卡间停留及结算停留不计时。零秒不能仅因小于一秒便被误判为无效，未完成必须用空值表示。
- **本轮边界**：从游戏首页开始第一关时创建新轮次，第二、第三关入口展示锁定状态，不再支持自由选择关卡或直接进入后续关卡。重新开始清空当前关和后续关的本轮状态，保留前序关本轮成绩；返回首页后再开始必须从第一关创建新轮次。
- **下一关解锁**：前端完成状态与服务端成功保存状态一致后才允许进入下一关。前一关保存失败时保留终盘并提供重试，不越过失败状态进入后续关卡。
- **历史与本轮分离**：重开或返回首页不删除已经成功保存的历史通关成绩。已经结算的总成绩不可被后续重开改写。
- **会话与多标签页**：初版每个账号只维护一个当前轮次，新开一轮使该账号之前未完成轮次失效；旧请求明确报轮次已失效，不与新轮次混算。切换账号后丢弃旧账号的待提交状态。
- **公开访问**：四个榜单可不登录浏览；写入成绩和读取个人最近记录必须登录。
- **分页**：默认每页 20 人，接口单页最多 50 人；无自动逐秒刷新，保留加载、空榜、错误和重试状态。

## 三、技术选型声明与最高优先级改进建议

沿用现有 SQLAlchemy/PyMySQL 数据访问方式，通过新增版本化 Flyway SQL 管理表结构。前端扩展现有排行榜占位页并新增三个可独立访问的单游戏页面，共享排行榜客户端、渲染逻辑和样式。保留现有海岛背景、深蓝、暖金与透明面板，不引入新框架、外部字体或常驻服务。

1. **优先确保逐关状态在前后端一致，再维护成绩事务。** 前端禁用未解锁入口，后端根据当前轮次检查前序关卡，禁止通过直接调用接口跳关；临时验收按钮也沿用同一顺序和成绩处理流程。认证后锁定用户或其轮次状态，顺序完成重复提交检查、写成绩、刷新最佳摘要、保留最近三次和清理其他成绩。最佳指向更新先于清理，异常时整体回滚，避免并发上传丢最佳、超量保留或出现悬空引用。
2. **完整轮次保存独立快照。** 总成绩保存本轮三项用时及其合计，不依赖单项历史记录永久存在；同一轮次和尝试版本具有唯一提交标识。已被清理或已失效的旧尝试重传不得被当作新成绩重新进入最近三次。
3. **使用可索引的最佳成绩摘要控制查询和资源开销。** 每位玩家每个榜单只保留一条最佳摘要，按榜单类型、用时、达成时间、用户排序；分页读取，复用现有连接池和有界执行槽。游戏计时在浏览器本地运行，只在轮次创建、重开、通关等必要事件请求后端。

## 四、数据库设计

复用现有 users、auth_sessions；新增以下三张表。字段名可在实施时按现有模型命名规范细化，但数据职责和保留规则保持一致。

### 1. 当前轮次状态表 challenge_progress

每个用户最多一行，用于验证本轮归属、游戏顺序、重开版本和重复提交；此表不属于历史通关记录。

| 字段 | 建议类型/约束 | 作用 |
| --- | --- | --- |
| user_id | INT UNSIGNED，主键、外键 | 关联现有用户，限制每人一个当前轮次 |
| run_id | CHAR(36)，ASCII、唯一 | 服务端创建的轮次标识 |
| revision | INT UNSIGNED | 轮次状态版本，隔离重开和过期响应 |
| game_state | JSON | 三关的尝试标识、是否完成、冻结用时和已接收提交信息；字段与大小由服务端固定校验 |
| total_recorded | BOOLEAN | 此轮总成绩是否已经结算 |
| created_at / updated_at | DATETIME(6) | UTC 轮次创建与最后更新时间 |

新轮次覆盖该账号旧的临时状态，历史成绩表中的快照不受影响。JSON 仅保存固定三关的有界状态，不能接收任意客户端结构。锁和事务统一使用一致顺序，避免死锁。

### 2. 通关成绩表 completion_records

统一存储单项和完整轮次两种快照，四类分别执行最佳与最近三次保留规则。

| 字段 | 建议类型/约束 | 作用 |
| --- | --- | --- |
| id | BIGINT UNSIGNED，主键 | 成绩标识 |
| user_id | INT UNSIGNED，外键 | 成绩归属，来自认证会话 |
| category | VARCHAR(16)，ASCII | mine、akari、sudoku、total；服务端白名单校验 |
| run_id | CHAR(36)，ASCII | 来源轮次，逻辑标识，不外键依赖可覆盖的临时轮次 |
| attempt_id | CHAR(36)，ASCII | 来源尝试，用于识别同一通关的重试 |
| duration_seconds | INT UNSIGNED | 冻结用时；total 为本轮三项之和 |
| mine_seconds / akari_seconds / sudoku_seconds | INT UNSIGNED，可空 | total 必须完整保存三项快照；单项记录不填其余项目 |
| completed_at | DATETIME(6) | 服务端记录的 UTC 达成时间 |

索引与约束：

- 唯一键 `(user_id, category, attempt_id)`，阻止仍保留成绩的重复插入。
- 索引 `(user_id, category, completed_at, id)`，读取最近三次并有界清理。
- 用户外键删除级联；时间、类别和合计一致性由业务校验及目标 MySQL 支持的数据库约束共同保证。
- `total` 只能由服务端汇总本轮状态生成，客户端不能直接上传总时长作为总榜成绩。
- 成绩一旦生成不可修改；最近三次按成功接收顺序计算。

### 3. 排行榜摘要表 leaderboard_entries

每个用户每个榜单最多一行，总榜只在完整三关成功结算后才有记录。

| 字段 | 建议类型/约束 | 作用 |
| --- | --- | --- |
| user_id + category | 联合主键 | 每人每榜唯一 |
| best_record_id | BIGINT UNSIGNED，外键 | 指向该类最佳成绩，清理时必须保护 |
| best_duration_seconds | INT UNSIGNED | 为排行榜排序保留的最佳用时摘要 |
| achieved_at | DATETIME(6) | 最佳成绩的达成时间 |

- 复合索引 `(category, best_duration_seconds, achieved_at, user_id)` 支持排序读取。
- 最佳引用和摘要在同一事务更新；业务确保引用属于同一用户和榜单类别。
- 不持久化名次。其他玩家刷新成绩后无需批量改写名次，查询时按同一排行规则计算。
- 前端显示的用户名通过关联 users 获取，不重复保存账号资料。

### 保留示例

某玩家扫雷记录依次为 40、35、50、45、60 秒。最佳为 35 秒，最近三次为 50、45、60 秒，最终保留四条。再通关 30 秒后，保留 45、60、30 秒三条；30 秒同时是最佳和最近一次，不重复保存。

完整轮次独立执行相同算法。保留一条总成绩不会迫使系统额外保留三个已淘汰的单项历史记录，因为三项用时已复制进总成绩快照。

### Flyway

新增 `backend/migrations/V2__create_ranking_tables.sql`，不修改 V1，不在启动时调用 ORM 建表。迁移依赖已有用户表；真实库执行前核对数据库与维护窗口。实际执行生产迁移属于后续部署范围，本次计划不包含上线操作。

## 五、接口与成绩提交流程

| 接口建议 | 用途与边界 |
| --- | --- |
| POST /api/challenges/start | 登录后创建服务端轮次；新轮次替换本账号旧临时状态 |
| POST /api/challenges/{run_id}/restart | 校验目标关本轮已经解锁；记录当前关重开，更新尝试版本并作废本关及后续关的旧请求 |
| POST /api/challenges/{run_id}/complete | 校验前序关本轮已通关及当前尝试有效，再生成单项记录；三关按序完成时自动生成总成绩 |
| GET /api/challenges/config | 返回开发验收按钮是否启用，不返回配置凭据；默认关闭 |
| GET /api/rankings/{category} | 分页读取 total、mine、akari、sudoku 榜单，仅返回公开字段 |
| GET /api/records/me?category=... | 登录后读取自己的最佳及最近三次，响应标明重合关系 |

具体流程：

1. 登录后从第一关创建轮次，返回轮次与第一关尝试标识；页面只有取得可用轮次后才允许开始挑战，不能为未解锁的后续关卡创建有效尝试。
2. 首次有效操作仍在浏览器本地起计时，不发送逐秒请求。
3. 通关时冻结用时，立即提交该关成绩，不等待用户点击“开始结算”；同一尝试重复提交返回已经接收的结果，不增加次数。
4. 后端在同一次有界数据库调用和事务中完成会话验证、轮次校验、锁定与记录维护，不把同一个数据库会话分派给并行线程。
5. 只有本轮按序完成三关，才能生成 total；后端用三项冻结值求和，重复打开结算不重复生成总成绩。
6. 处理网络丢包、乱序到达和响应丢失：前端按事件顺序提交，后端检查版本；前序未成功保存时不生成总成绩。提供明确的待保存、保存失败和重试提示，不提前显示“已上榜”。
7. 未收到的旧版本和已失效轮次明确拒绝；已处理版本的状态由当前进度维护，即使对应旧成绩已被清理，也不能重放成新的通关记录。新轮次替换旧进度后，旧 run_id 一律拒绝。
8. 重开、退出或换号时处理待提交状态，不能把旧请求计入新轮次或新用户；已完成历史成绩保持不变。
9. 无论通过入口点击、手工派发事件或直接请求后端，未完成本轮前序关都不能进入或提交后续关。已经失效的前序版本不能作为解锁依据。

写接口复用 Cookie 会话和同源校验，用户 ID 由后端取自会话。针对新增写接口补齐现有请求体上限覆盖，限制字段和整数范围；普通读取不执行密码哈希。没有 Redis、后台常驻清理任务或每秒轮询。

### 当前可信边界

现有棋盘和计时均在浏览器执行。本次可以校验身份、轮次、顺序、字段和重复提交，但这些措施不能证明浏览器上报的用时及通关结果未被人为修改。本计划保持现有游戏执行方式；完整服务端判题及操作回放验证不在本次范围，不能将完成后的榜单描述为已经实现严格防作弊。

## 六、页面与交互设计

- 主页沿用 `frontend/ranking.html`，新增 `ranking-mine.html`、`ranking-akari.html`、`ranking-sudoku.html` 三个分页面，可独立打开及使用浏览器前进后退。
- 四页共用“总榜 / 扫雷 / 照明 / 数独”二级导航，标出当前页面，顶部保持现有站点导航和账号入口。
- 榜单核心列为名次、用户名、最佳用时；总榜可展开查看该最佳轮次的三项用时，不混用单项最好成绩。
- 清晰展示参与资格、同秒并列规则和每页条数。无成绩时显示空榜说明，不放虚构玩家或演示成绩。
- 沿用现有深蓝、暖金、海岛与透明卡片，使用系统中文字体；数值使用等宽数字样式。
- 手机优先，长用户名不挤压时长；窄屏减少并列信息或将三项明细展开为卡片，避免页面整体横向溢出。
- 保留加载、无数据、加载失败和重新加载状态；快速切换页面或重试时丢弃旧响应，防止错误榜单覆盖当前结果。
- 用户名以 textContent 渲染；导航使用真实链接，按钮至少 44px，键盘焦点可见。
- 启用结算里的“查看排行”入口，正确标明本轮是否已保存和是否具备总榜资格。
- 游戏首页删除“自由选择关卡”说明，第二、第三关显示锁定及解锁条件；只提供从第一关开始新一轮的入口。
- 下一关按钮只在当前关通关并成功保存后启用；网络失败时展示“重试保存”，不能提前解锁下一关。

### 开发阶段临时一键通关

- 明确标注“开发验收：一键通关”，仅开发配置显式启用时显示；建议配置项 `DEV_QUICK_COMPLETE_ENABLED=false`，默认关闭，由服务端配置决定，不通过 URL 参数或浏览器存储开启。
- 按钮只作用于当前已经解锁、正在挑战且尚未通关的关卡，不自动完成后续关卡。扫雷和照明成功保存后提供正常的下一关入口，由玩家点击进入；数独成功保存后进入正常的祝贺与结算流程，不允许直接伪造 total。
- 复用正常的计时冻结、通关结果、成绩提交和结算流程，不只弹出成功提示。尚未开始操作时，点击验收按钮作为首次操作起点，不生成伪造的负数或未完成时长；沿用整数秒口径允许零秒。
- 开发通关请求携带明确标记，后端在开关关闭时拒绝该验收路径；开关读取失败时保持关闭，正常游戏不受影响。
- 在专用开发/验收数据库中验证排行榜写入，开发配置示例注明用途，生产配置保持关闭。临时完成记录不导入正式排行榜数据库。
- 保存期间禁用重复点击，失败允许使用同一尝试标识重试。新轮次、重开、换号和开发按钮均遵循同一隔离与幂等规则。
- 临时交互及处理代码集中组织并注明用途；后续按用户要求移除按钮、专用处理和配置，并验证正式通关流程不依赖验收代码。

页面设计参考 ui-ux-pro-max 的表格响应式建议；通用设计检索返回的营销页结构不适合本项目，因此不采用。实际布局继续以现有项目风格和手机榜单可读性为准。

### 模块一：数据与排行榜后端

产出：V2 迁移、三个数据实体、请求响应模型、对应 Repository/Service/Controller、路由注册和必要的业务/API 测试。

## 八、验收用例摘要

| 场景 | 预期 |
| --- | --- |
| 本轮只通关扫雷 | 扫雷单项有成绩，解锁照明，不进入总榜 |
| 首页直接点击第二、第三关或派发入口事件 | 保持锁定，不启动后续游戏计时 |
| 未通关前序关，直接请求重开或提交后续关接口 | 后端拒绝，不生成成绩或解锁状态 |
| 本轮通关扫雷但保存失败 | 保留终盘并允许重试，照明暂不解锁 |
| 有历史三关成绩，但当前是新一轮 | 仍必须从扫雷开始，不继承历史解锁 |
| 逐关完成，或重开当前关 | 按序解锁，重开清空当前与后续本轮状态 |
| 同一轮三关分别 65、130、245 秒 | 总榜记录为 440 秒，并保存这三项快照 |
| 多轮中单项最好成绩合计小于任一轮总时长 | 总榜仍取最好完整轮次，不拼接单项 |
| 一类成绩保存五次，最佳在最近三次之外 | 恰好保留四条，即最佳与最近三次 |
| 最佳位于最近三次之内 | 恰好保留三条，不复制最佳 |
| 已有最佳 35 秒，再通关 35 秒 | 原最佳达成时间不变，新成绩进入最近三次 |
| 同一玩家重复请求、响应丢失后重试 | 不多记一次，不影响最近三次排序 |
| 被清理的旧尝试重新提交 | 不复活为最新通关 |
| 两次提交并发到达 | 最佳、最近三次和摘要一致，无悬空引用 |
| 单项旧记录被清理，但总成绩仍在保留集合中 | 总榜三项明细仍完整可读 |
| 两位玩家秒数相同 | 并列名次且展示顺序稳定，后续名次跳号 |
| 页边界包含同分玩家 | 跨页名次仍依据全部更快玩家数量计算 |
| 上一轮请求晚到、重开后旧请求到达或中途换号 | 不污染新轮次，不把成绩记到新账号 |
| 后端/网络失败、连接池或执行槽繁忙 | 明确提示并可重试，不显示已保存成功 |
| 开发验收开关关闭或配置请求失败 | 临时按钮不可用，后端拒绝专用验收调用，正常挑战可继续 |
| 专用开发环境在扫雷或照明点击一键通关 | 仅完成并保存当前关，提供正常下一关入口，后续关卡仍未完成 |
| 专用开发环境在数独点击一键通关 | 仅完成并保存数独，按正常流程生成本轮总成绩并展示祝贺与结算 |
| 当前关已经完成后再次触发验收操作 | 不重复通关、提交或自动进入下一关 |
| 临时通关按钮重复点击或保存响应丢失 | 同一尝试只记一次，失败可重试，不跳过关卡状态 |
