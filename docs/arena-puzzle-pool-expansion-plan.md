# 竞技独立题库扩充与近期去重计划

日期：2026-10-27（北京时间）。需求已明确：照明、数独各20道独立原题；按双方账号各自最近4局去重。用户已明确“开始实现”，本计划已授权执行，验证结果见arena-puzzle-pool-expansion-report.md。

## 需求与边界

- 照明保持10×10、约闯关第10关难度；数独保持简单9×9。现有竞技时限、双方同题、棋盘操作、自动提交、结算和积分规则不变。
- 两种游戏各有20个稳定原题身份。保留符合要求的既有原题，补足独立题目；不以旋转、镜像或替换数字充当额外原题。
- 选题避开两位玩家在该游戏中各自最近4局的原题。换对手、重新匹配、重新建房和服务重启后仍有效；两种游戏分别记录。
- 同一原题的任何展示变换都使用同一个原题ID。题库变换可以保留，但不增加原题数量，也不绕过去重。
- 正式开局时才计入历史；准备前取消、邀请失败和未开始的倒计时不计入。已经开局后退出或超时仍计入，因为题目已向玩家展示。
- 扫雷、闯关目录和奖励不在本轮改动范围；不新增用户界面或额外常驻服务。

## 技术选型声明与最高优先级

沿用Python/FastAPI、MySQL、Flyway及现有单进程竞技事务。开发机离线生成并审核版本化题库，线上只读取已审核题目、选题和验证终盘，不运行生成器或唯一解搜索。

最高优先级：先确保每种游戏确有20道合格的独立原题，再确保双方账号历史按原题身份持久化去重。不能以扩大随机变换数量替代扩充独立题库，也不能只依赖当前房间或浏览器存储实现去重。

## 题库设计

新增冻结竞技题库版本与离线审计文件，不覆盖旧题库、闯关定义或已经保存的房间题目。每道题包含原题ID、题库版本、游戏、尺寸、题面及配置来源；审计文件记录生成种子、唯一解和难度验证结果。解答与审计轨迹不通过正式房间接口下发。

照明逐题检查合法性、唯一解、与第10关相同的逻辑层级及接近的推理规模；独立原题需有不同墙体布局，排除旋转/镜像等价图。数独逐题检查唯一解及既有简单难度分级，不引入高级推理；独立生成题目并做规范化判重，排除仅换数字或方向的复制题。上述离线指标用于保持同档难度，不宣称每道题的人类实际用时完全相同。

## 服务端选题与记录

1. 每个账号、每种游戏只保存最近4局的原题ID及必要局标识，记录长度有上限，读取走主键或对应索引，不扫描历史房间。
2. 双方准备完成、冻结下一局题目时，读取双方近期集合，从20道题中排除其并集，再随机选择。两个集合最多排除8道，正常至少有12道可选，不需要用重复题兜底。
3. 为该局保存原题ID、题库版本和冻结题面，双方读取相同快照；刷新、重连和重复准备不能换题。
4. 倒计时进入playing时，与房间状态转换在同一事务更新双方近期记录，每局每人仅记一次。沿用现有统一锁及账号锁顺序，处理同时准备、维护任务与重试。
5. 等待房间和未开局重赛不提前消耗历史记录；更换对手后在最终冻结题目时再次按双方历史校验。
6. 旧局继续使用已有快照并正常结算。服务重启释放或作废房间仍沿用既有规则，近期题目记录保留。

## 数据库与部署

新增近期记录所需结构通过下一版本Flyway迁移管理，当前工作区最高V21，实施前复核，预计使用V22。记录空间按账号和游戏有界，不追加无限增长的去重流水。

本轮属于后端与内容更新，需要新API镜像、题库文件及增量迁移，不用此前纯前端补丁替代。保留正式配置、旧迁移、账号和积分。开发与验证均在本机隔离环境执行，不连接或部署业务服务器。

## TDD与验收步骤

1. 先补失败测试：每种游戏20道、稳定原题ID、独立性、唯一解、难度与尺寸；近期4局、双方历史并集、变换不绕过去重、历史长度上限。
2. 离线构建及审计新题库，再接入服务端选题；方法、脚本用途和关键参数加注释。
3. 实现持久近期记录及开局事务，覆盖换对手、重新匹配、重赛、取消倒计时、重复维护、异常回滚与重启。
4. 验证双方同题、开局前不发题、旧局恢复、合法终盘及积分不受影响。
5. 在隔离MySQL5.7与真实Flyway验证新增迁移、生产autoflush=False会话及并发/持久化；运行受影响API回归与双浏览器多局抽题验证。
6. 完整测试输出写入artifacts日志，只报告失败摘要或最终统计；不重复执行未受改动影响的相同测试。
7. 更新项目目录树、实现说明与发布步骤；通过后按功能使用中文描述提交，并交付对应后端更新材料。
