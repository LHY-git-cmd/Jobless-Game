# 关卡成长、外观解锁与双人竞速完整实施方案

日期：2026-10-21（北京时间）。

状态：本文件为方案交付，不是实现或容量验收报告。本轮仅创建文档及维护目录树，不修改游戏、API、数据库或部署。用户已确认最高星级/一次性经验/首次三星加成/星数不消费、统一账号等级/四组解锁/离开继续计时、先房间后匹配/首版无段位观战及成长奖励；另明确PK必须先通过扫雷初级、照明第1关、数独初级。前端视觉、布局、动效及交互稿由用户后续提供。未单独确认的具体数值仍为建议，不能当作已上线规则。

## 1. 目标、范围与技术选型声明

目标：以照明十关验证成长循环，为扫雷/数独初级补正式通关验证以实现三游戏PK前置，再扩展双人房间和自动匹配。前后端通过统一RESTful HTTP资源交互，服务端确认奖励、解锁、计时与对局结果。

| 层次 | 选型与边界 |
| --- | --- |
| 前端 | 保留多页HTML/CSS/原生ES Module；规则、控制器、目录数据与API客户端分开；视觉等用户后续设计 |
| 后端 | FastAPI单Uvicorn进程，Controller→Service→Repository；现有有界线程执行器和数据库连接池 |
| 数据库 | 现有MySQL/InnoDB，兼容项目MySQL 5.7约束，Flyway新增迁移，不修改已执行V1～V4 |
| HTTP契约 | 新增能力统一`/api/v1`，资源名称使用复数名词，正确使用GET/POST/PUT/PATCH/DELETE和HTTP状态码 |
| PK推送 | RESTful HTTP承担全部写操作；SSE提供只读事件流，GET可读取权威快照；首版无需WebSocket |
| 题目与素材 | 预设题库，开发机完成唯一解验证和打包；Nginx提供可缓存的样式/素材，PK题目由受控接口发放 |
| 常驻服务 | 复用宝塔Nginx/MySQL与单API，不新增Redis、Celery、消息代理或独立匹配服务 |

最高优先级建议：先建立稳定关卡身份、服务端尝试与幂等奖励事务，再建设成长页面或PK。现有客户端用时、旧成绩和本地练习存档不能直接转为成长奖励凭据。

本轮不包含生产部署、正式迁移、界面实现。后续实现分阶段验收，不一次性上线所有系统。

## 2. 已知现状与需要补齐的基础

1. 扫雷练习已有10×10/15×15/20×20九关，本地按用户/游客隔离，不写正式成绩；保持原样，不批量兑换经验。
2. 现有照明为一个固定10×10题盘，算法读取模块级全局地图。需改为读取关卡实例的尺寸和地图，才能支持十道题。
3. 现有挑战协议仍以mine/akari/sudoku三个数组位置表示，通关接收客户端用时。它不具备新成长系统所需的关卡级身份、服务器计时及终盘验证。
4. 现有成绩只保留最佳与最近三次，其余记录会删除。首次通关/首次三星/奖励凭据必须独立保存，不能依赖这批可清理记录。
5. 登录使用HttpOnly Cookie，现有同源写请求校验和账号/轮次隔离可复用；新接口必须纳入请求体上限，不能遗漏`/api/v1`路由。
6. 当前部署是单进程、`--limit-concurrency 32`，API容器上限320MiB/1 CPU；MySQL池3、无溢出，数据库线程槽4。长连接不能长时间占用这几个数据库槽。
7. 目标2核/2GB与宝塔/其他服务共存，目前没有新的目标机容量证据，不承诺在线人数。

## 3. 建议玩法规则与明确可调整参数

成长语义与四组解锁/计时已获用户确认；具体经验、等级阈值、主题门槛和PK超时数值作为推荐起点。最终配置冻结后写入版本化文件，避免业务代码散落阈值。

### 3.1 星级与时间

- 每关历史最高0～3星；0星表示未通关。合法通关至少1星，较快通关2或3星。
- 每题配置`t3_ms < t2_ms`，用时不超过`t3_ms`为3星，不超过`t2_ms`为2星，其余合法通关为1星。
- 每题阈值通过人工试玩确定；不能用同一阈值评价所有题，不按玩家群体在线重算。
- 首次点击“开始”创建正式尝试并由服务端记起点；首次规则阅读不计时；之后查看规则、离开、断网均继续计时。
- 服务端使用UTC微秒时间，按毫秒比较阈值，界面只显示格式化秒数。提交体不得指定计时结果。
- 网络往返会影响服务器接收用时，实验版接受这一有限误差，不以客户端自报时间消除误差。星级阈值留合理余量。
- 总星数为各稳定关卡历史最高星级之和，仅增加差值：1→3增加2；再次3星增加0。题目修订不能重复发星。
- 上线后评分规则/题目有实质变化应使用新版本；旧奖励保留，不通过提高阈值回收已经获得的成长。

### 3.2 经验与等级（建议数值）

| 里程碑 | 单关一次性经验 |
| --- | ---: |
| 首次合法通关 | 30 |
| 首次获得第1颗星 | 10 |
| 首次获得第2颗星 | 10 |
| 首次获得第3颗星 | 10＋首次满星额外20 |

一关最高80经验。首次直接三星获得全部80；先一星获得40，随后提高到三星再获得40，累计相同。“首次满星”指第一次达到三星，不要求第一次尝试就三星。未提高星级的重复通关只更新合法成绩，不发经验。

账号等级统一，经验只由服务端累计。实验阈值建议为Lv.1=0、Lv.2=90、Lv.3=180、Lv.4=270、Lv.5=500、Lv.6=800；十关最大800经验，先不设计无上限等级曲线。

### 3.3 十关解锁（建议）

| 照明关卡 | 等级要求 | 前置要求 |
| --- | --- | --- |
| 1～3 | Lv.1 | 无，供初次探索 |
| 4～6 | Lv.2 | 第3关至少1星 |
| 7～9 | Lv.3 | 第6关至少1星 |
| 10 | Lv.4 | 第9关至少1星 |

无死锁证明：前三关各1星可得120经验，足够Lv.2；前六关得240，足够Lv.3；前九关得360，足够Lv.4。无需满星或重复刷关。用户可以提前高星升级，但仍需完成指定前置关。

首版仅这十道照明题发放本节成长奖励；扫雷/数独各新增一个正式初级资格关，记录通关但暂不发经验/成长星，避免未设计难度评价就影响等级曲线。现有其他练习模式保留，后续按游戏扩展成长。锁定原因由API返回，不让前端自行推断。

### 3.4 外观（建议）

- 累计星数门槛，星星不消费、不减少，达到条件永久解锁。
- 首版提供默认主题＋一个实验主题；建议10星解锁实验主题。账号保存已拥有外观和当前装备。
- 首版只改变配色、边框和轻量棋盘皮肤，后续具体外观由用户设计。不影响线索辨识和星级/计时。
- 游客可本地预览，不领取正式成长或账号权益。锁定外观不能靠修改前端参数装配为账号已拥有。
- 不包括货币、商店、支付、交易、付费皮肤、每日任务。

### 3.5 PK前置资格（用户明确要求）

必须同时满足三项正式通关：

| 要求 | 对应稳定关卡 | 通过标准 |
| --- | --- | --- |
| 扫雷初级 | `mine-beginner-001`，10×10/10雷 | 排开全部安全格且未踩雷 |
| 照明第1关 | `akari-001` | 合法通关至少1星，不要求满星 |
| 数独初级 | `sudoku-beginner-001`，经验证的初级9×9题 | 保留题目数字并完成有效终盘 |

三项初级关卡始终开放，不以PK、等级或后续关卡为前置。全部条件是AND，不是任意一项；正式完成后资格长期保留，不因重开、成绩清理、退出或重启而取消。

扫雷“初级”本次定义为上述10×10/10雷正式入门关；数独现有题目未证明是初级，不能只改标签，应制作/验证合适的新题。具体题目在内容阶段确认。

资格只来自服务端验证的新尝试。现有本地`mine-easy`或旧正式客户端自报成绩不自动补资格；页面明确指向可获得资格的正式入口。测试/开发通关、游客练习不计入。

服务端在创建房间、加入房间、创建匹配票和实际配对时检查资格；不满足返回403、`code: pk_locked`及逐项缺失状态，不能只依赖前端隐藏按钮。

## 4. 关卡目录与照明十关

稳定身份：`level_id`（如`akari-001`）、`game_id=akari`、`level_version`、`rules_version`、`reward_policy_version`；题目版本决定棋盘/评分，奖励权益唯一身份仍以稳定关卡ID＋里程碑为准。

每题配置：序号、名称、行列数、地图、难度标签、2/3星阈值、前置关卡、最低等级、可用模式、发布时间、内容校验值。官方目录及评分配置是服务端权威；构建时生成供前端展示的公开元数据，避免前后端手抄两套。

十关内容建议：1～3基础照射/黑墙，4～6数字线索组合，7～9交叉约束，第10关综合。题目数量先固定十道；尺寸、具体地图与时间阈值在题库制作和视觉设计阶段试玩确认，不能把未经验证的随机地图发布为正式题。

开发机构建检查：地图字符和尺寸合法、至少一个白格、线索范围合法、有解且唯一解、标准解通过规则验证、分组可达、时间阈值有序、奖励不会因题目版本重置。唯一解搜索在开发机/CI离线执行，服务端通关只检查提交布局是否满足规则。

照明规则模块改为`createAkari(level)`、`inspectAkari(state)`等实例输入；所有邻接、照射、渲染以当前尺寸和地图为准，默认调用保留现有题盘以兼容旧页面/存档。

## 5. RESTful API统一规范

### 5.1 基本契约

- 基址`/api/v1`；小写复数资源名、短横线；URI标识资源，不使用`/getLevels`、`/addXp`、`/startGame`、`/completeGame`。
- GET/HEAD只读；POST创建服务器分配ID的资源；PUT创建/完整替换明确地址的资源；PATCH仅修改允许变化的字段；DELETE删除成员关系/排队票等可删除资源。
- 成功GET=200，创建=201并带Location，更新=200/204，删除=204。仅真正异步接受任务才用202，本方案普通结算同步完成，不滥用202。
- 401未认证、403无权限/未解锁、404不存在或不属于本人、409业务状态/幂等冲突、410尝试/排队票已失效、412版本前置条件失败、413体积超限、422字段/终盘不合法、429频率超限、503服务容量不足；429/503带Retry-After。
- JSON字段snake_case；ID按不透明字符串处理；UTC时间使用带Z的RFC3339格式；用时字段`duration_ms`整数；经验`xp`、星数`stars`整数。
- 分页采用稳定游标，`limit`默认20最大50，响应`items`、`next_cursor`、`links`；已知只有十关时一次返回有限目录，不开放无上限列表。
- 返回资源包含相关`links`（self、attempt、completion等），前端不依赖对象内部数据库ID结构。
- Cookie同源认证；写操作继续校验Origin/Referer。DTO禁止额外字段；客户端不得指定user_id、awarded_xp、stars、winner_id或可解锁状态。
- 对账号私有/动态API统一no-store，静态素材沿用缓存。正式HTTPS启用Secure Cookie。SSE是独立流式客户端，不套JSON客户端十二秒超时。

HTTP状态码与条件请求依据[RFC9110](https://www.rfc-editor.org/rfc/rfc9110.html)。

### 5.2 幂等、版本与错误

- 创建型POST要求`Idempotency-Key: UUID`；唯一作用域为账号＋资源类型＋键。同键同规范化负载返回最初结果/Location，同键不同负载409。
- PUT通关结果是不可变单例：首次成功201；相同终盘重放200且奖励增量仍为原结算，不再次加经验；不同终盘覆盖已完成结果409。
- 可变资源（账号外观、尝试放弃、准备状态）GET返回ETag；修改带If-Match，版本不匹配412，缺少必需前置条件返回428。409用于状态冲突，不能混为版本冲突。
- 幂等识别先于“账号已在对局/达到尝试上限”等可变条件，避免响应丢失后的合法重试被错误拒绝。
- 新API使用RFC9457 `application/problem+json`：`type`、`title`、`status`、`detail`、`instance`，扩展`code`、`field_errors`、`request_id`、必要的资源链接。日志不打印密码、Cookie或终盘完整内容。

错误示例：

```json
{
  "type": "urn:jobless:problem:level-locked",
  "title": "关卡尚未解锁",
  "status": 403,
  "detail": "需要达到Lv.2并通过第3关。",
  "instance": "/api/v1/attempts",
  "code": "level_locked",
  "requirements": {"minimum_level": 2, "prerequisite_level_id": "akari-003"}
}
```

错误结构依据[RFC9457](https://www.rfc-editor.org/rfc/rfc9457.html)，只应用于新版本接口；保留旧接口detail兼容行为。

| --- | --- | --- |

### 5.4 旧接口兼容与RESTful迁移

当前`/api/challenges/start`、`/.../restart`、`/.../complete`属于既有动作式路径，不能宣称全项目已经统一RESTful。新增功能先全部遵守v1资源规范；旧页面保持可用，通过兼容适配层调用共同Service，不复制结算业务。

后续对应模块改造时迁移认证到`POST /sessions`、`GET /me`、`DELETE /sessions/current`，论坛到`/posts`、`/posts/{id}/comments`、`/posts/{id}/likes/me`等资源；迁移前冻结OpenAPI和原行为测试。旧路径在所有页面/验收脚本/部署都迁完并得到确认前不删除，不采用改变HTTP方法的重定向替代兼容层。

客户端公共http工具需支持自定义Idempotency-Key/If-Match、读取ETag/Location，以及新旧错误格式映射；业务客户端只依赖资源契约。分页、权限、缓存与状态码按模块同批迁移。

## 6. 服务端尝试、结算与一致性

### 6.1 尝试生命周期

`active → completed | abandoned | expired`，终态不可逆。每账号每关最多一个active，最多十个正式活跃关卡；同关重开先幂等放弃旧尝试再创建新尝试。未放弃而重复创建返回409及已有资源链接，Idempotency-Key重放除外。

正式开始POST才返回尝试绑定的题目；开始前只返回规则与元数据。固定题可能已被玩家记住，故该机制不能防止背题/自动解题。仅做服务器计时、账号/版本校验、终盘验证和奖励防重，不宣传严格竞技反作弊。

### 6.1.1 三游戏初级正式验证

- 照明：提交灯泡坐标，验证覆盖、互照和数字线索；`akari-001`合法成长结算时同事务授予照明资格。
- 数独：服务端绑定一题初级题；提交81格终盘，验证范围、题目数字不变、每行/列/九宫包含1～9，无需服务端在线搜索答案；qualification完成只授资格，不套用照明经验策略。
- 扫雷：服务端生成并保存本次10×10/10雷隐藏布局，不把完整雷图/可推导雷图的种子提前发给客户端。揭格通过上述幂等PUT提交索引，服务器计算连续展开和胜负，响应只包含已揭开的线索；插旗/选中可保持浏览器本地状态。踩雷后才发失败终盘，胜利后completion校验服务端won状态并授资格。
- 正式扫雷因此需要一个网络适配层；原本本地扫雷练习引擎继续用于练习，不能原封不动拿本地won标志换资格。每次揭格是玩家动作请求，不是逐秒轮询；最多100个格子，有界布雷/展开/短事务，在资源验收中单独测量。
- 并发揭格按尝试串行，先到踩雷形成lost后拒绝新的揭格；已处理同索引返回其确定结果/最新终态。断网时先显示待确认，恢复GET权威已揭棋局，不把本地猜测当作服务器结果。
- 三项资格写入`player_qualifications`，唯一键`(user_id, requirement_id)`，附首次通过时间、正式level/version和attempt标识。尝试清理不删除资格。

尝试有效期建议7天；过期返回410且不发奖励，本地可保留棋盘作为练习。照明/数独的中间操作先在localStorage即时保存，不逐步上传，也不承诺跨设备恢复未上传中间盘；正式扫雷的已揭状态由服务端保存，本地只保存选中/插旗等辅助状态。服务端永久保存已确认星级/等级等账号成果。页面恢复必须GET对应尝试核验，客户端时间只用于显示估算。

服务端记录`received_at`早于数据库槽位等待，完成验证成功后用该接收时间结算，避免数据库排队被计入玩家成绩。过载未接受的请求503不产生成绩，需要客户端按原请求重试。后端异常及验证失败不能消耗首次奖励。

### 6.2 单次结算事务

1. 校验来源、请求体/灯泡数量/坐标范围，认证当前账号；读取与尝试绑定的不可变题目版本。
2. 按尝试绑定游戏验证：照明检查至多20×20布局（首版建议≤10×10），拒绝重复坐标、黑格灯泡、互照、未照亮和线索不满足；数独验证81格终盘；扫雷核对服务端won状态。
3. 固定顺序锁账号成长行→尝试→该关进度行；重新检查所有权、状态、版本和过期。
4. 已完成且规范化布局相同，返回原结算；已完成但不同，409。
5. campaign由服务端计算时间/星级，只增加最高星差值，插入未领取里程碑并更新经验；qualification仅保存通关与资格，不发照明成长奖励。
6. 计算等级/解锁门槛，插入满足条件的新外观权益；保存完成资源、响应快照及状态。
7. 一个事务提交，再返回响应；任一步失败全部回滚。推送失败不能回滚已提交成果，前端通过GET恢复。

按`(user_id, level_id, milestone)`建立奖励唯一键，题目/奖励策略版本不进入该权益唯一键。首次插入进度或成长行的竞争按用户锁串行处理，不能先查未领取再在无锁事务中发奖。

账号成长及外观等正式成果跨设备可查询；本地存档只负责未上传棋盘。JSON只放大小有界的地图/快照，不把所有玩家或所有历史对局合并到一个大JSON行。

新增Flyway阶段建议：V5关卡/尝试/完成/成长/幂等/资格；V6外观；V7房间/成员/提交/PK占用；V8匹配票，并为既有PK占用表增加对应票据关联。实施时先确认实际最大版本号，若已被其他工作占用则顺延，绝不覆盖已有迁移。

清理由单次有界脚本完成，每次例如200行/批、最多10批；建expires_at索引，按父子顺序处理外键，保留奖励与权益，永久记录不因尝试被清理而级联删除。脚本作用及关键参数必须有注释，不额外启动常驻清理服务。

容量估算只给数量关系：U个账号、L个关卡，关卡进度最多U×L行，奖励凭据最多4×U×L行，账号摘要U行；实际磁盘/索引大小必须用MySQL数据测量。尝试历史按日创建量×保留天数计算，不把数据库磁盘容量当作常驻内存大小。

## 8. PK阶段一：双人房间码同题竞速

### 8.1 建议玩法

- 必须先正式通过扫雷初级、照明第1关和数独初级，三项AND；首版对战游戏为照明，独立PK题池，双方相同题目/版本，最多2人。对局结果不产生单人星星/经验/外观权益。
- 房间码只是加入定位码，不是身份凭据；成员仍需Cookie认证。房间码有过期时间，随机生成、碰撞检查；加入/猜码请求限流。
- 两人确认准备后服务端安排5秒倒计时并冻结题目。只在开始时发题，倒计时前不能通过GET或事件流取到地图。
- 浏览器显示统一`starts_at`和本地平滑倒计时，服务器禁止开始前提交。倒计时后发题存在网络差异，首版定位娱乐竞速，不能承诺毫秒公平。
- 仅同步就绪、开始、在线/断线、有效完成、结束，不实时公布灯泡位置或未经验证的完成百分比。
- 建议比赛时限10分钟；离线重连宽限30秒。进行中一方主动退出判负；双方同时离线或服务重启导致中断则作废，不发奖励。
- 比较服务端收到且验证通过的布局时间；首个有效提交打开1秒平局窗口，另一方在该窗口内有效提交为平局，否则先提交方获胜。窗口参数为娱乐模式建议，待用户确认。
- 提交接收时间须在HTTP入口记录，不能由数据库处理先后决定胜负；结算房间前排空/核对窗口内已经接收的有界验证任务，避免任务排队造成误判。

### 8.2 RESTful PK资源

| 方法与路径 | 用途/语义 |
| --- | --- |
| POST /rooms | 创建房间，`{game_id:"akari",difficulty:"normal"}`＋Idempotency-Key，201＋Location；校验三项资格 |
| GET /rooms/{room_id} | 成员读取权威房间快照，地图只在开始后且成员有权时返回 |
| POST /room-memberships | `{room_code}`创建自己的成员关系，201＋Location，校验三项资格/容量/过期/状态 |
| DELETE /rooms/{room_id}/members/me | 离开房间，204；进行中根据规则结算，不删除历史结果 |
| PUT /rooms/{room_id}/members/me/readiness | `{ready:true}`＋If-Match，创建/替换自己的准备状态 |
| PUT /rooms/{room_id}/submissions/me | `{bulbs:[...]}`创建不可变有效提交，首次201，同内容200；非法布局422，可修正后再交 |
| GET /rooms/{room_id}/result | 读取已结算结果，无结果404，不能用GET触发结算 |
| GET /me/rooms?status=active | 重连/重新打开页面时找到自己的房间 |
| GET /me/events | `text/event-stream`，仅本人有权资源变更通知，单向只读 |

全部路径基于`/api/v1`。玩家每次只能拥有一个活跃PK身份（排队或房间），防止双重匹配及自己匹配自己；首次实验每账号最多一个事件流连接。

房间状态：`waiting → countdown → playing → finished`；另有`cancelled`、`expired`。等待超时建议5分钟；倒计时中成员离开则取消本次倒计时，剩余成员重新准备后才能开始；服务重启将所有未完成房间标记cancelled/reason=server_restart，不恢复比赛计时竞争。

房间快照和事件不能泄漏对手终盘、未开始题目或标准答案；客户端只提交自己的解答。服务器定时状态转换（倒计时结束、过期、重连期限）由单个有界调度器执行，GET只读取已提交状态，不通过读取触发比赛开始或胜负结算。

## 9. RESTful与实时推送的关系

为了满足本项目RESTful要求，调整此前的WebSocket建议：所有业务修改都通过上述HTTP资源完成，实时性只用SSE的HTTP GET长响应。SSE提供通知，不接受`join/start/win`等命令；不能把SSE本身宣传为完整REST架构，RESTful约束主要落实在资源、方法、表示、权限和状态码。

事件示例：`event: room-updated`，`data: {resource:"/api/v1/rooms/...", revision:12}`。前端收到变更后GET快照；可以合并同一资源短时间内重复通知。计时/心跳不触发数据库查询。EventSource及事件格式依据[HTML SSE规范](https://html.spec.whatwg.org/multipage/server-sent-events.html)。

每人单连接复用房间和匹配事件；队列最多16条小通知、单条最大2KiB，慢客户端关闭后重连读取当前快照；不是无限历史回放。Last-Event-ID在当前有界缓冲内可续接，否则发送resync通知；重连时始终GET当前房间/票据，因此事件丢失不丢结果。

鉴权在短数据库调用中完成后立即释放连接/线程槽，再开始流式响应；不能让yield依赖在长连接期间保留数据库Session。连接有最大寿命，建议60秒重新验证一次Cookie/会话，退出登录主动关闭，服务端撤销本进程账号流。对局写请求每次重新鉴权。

SSE心跳建议15秒，仅写注释，不写数据库；Nginx该路由单独关闭proxy_buffering/cache并将读取超时设为60秒或更长，维持普通API原有短超时。参数依据[Nginx代理文档](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)。

## 10. PK阶段二：自动匹配

REST资源：POST `/matchmaking-tickets`创建排队票（校验三项资格，game_id、difficulty、Idempotency-Key）；GET `/matchmaking-tickets/{id}`查询；DELETE该资源取消等待（重复删除204）；GET `/me/matchmaking-ticket`恢复自己的当前票。成功配对更新票据的room链接并通过SSE通知。已配对票不能通过取消票退出对局，应按成员退出规则处理。

仅一个照明匹配池，初期按指定难度＋先到先配对，不按账号等级推断实力；不引入段位、跨服、机器人、观战、聊天或多人混战。排队建议60秒超时，明确显示无人匹配，不无限等待。

单进程内存负责等待队列索引与事件连接，MySQL记录票据和房间。匹配时固定顺序锁两名用户的PK占用记录，再核对票状态并原子写两张票＋房间/成员。取消与配对竞争只能有一个结果；事务提交后才更新内存缓存/发通知。服务异常时数据库是权威，当前队列索引可重建；重启的等待票统一取消，不悄悄维持失效匹配。

按到达、取消、过期事件驱动配对，定时任务只处理有界活跃集合；禁止每秒全表搜索玩家或为每名玩家开一个轮询数据库任务。

## 11. 前端逻辑边界（视觉待用户提供）

需要的功能视图：关卡目录/锁定原因、规则确认、棋盘与计时、结算星级/经验差值、账号成长、主题预览/装备；后续房间创建/加入/准备/倒计时/对局/结果、匹配等待/取消/重连。页面如何布局、导航和动画暂不固定。

模块建议：`games/akari`规则/关卡数据；`progression`成长客户端/显示模型；`cosmetics`权益/装配；`pk`房间/匹配客户端和SSE订阅；`pages`只装配。公共http支持请求头和新错误格式，流式客户端独立。尽量随功能整理相关模块，不为本方案先大规模搬动论坛/认证目录。

前端只展示服务器星数/经验/解锁结果，允许先显示“正在确认”，不在本地乐观加正式奖励。失败重试冻结原终盘和幂等键，账号变更立即销毁订阅/棋盘/旧请求资格。主题通过语义CSS变量和版本化素材切换，视觉状态不能只靠颜色表达。

前端设计确认前可完成后端契约、规则和题库校验、测试客户端/最小验收夹具，不定稿产品页面。任何临时验收工具与最终玩家界面区分。

## 12. 2核/2GB资源预算、保护及验收

### 12.1 保留现有边界

API继续一个worker、320MiB容器上限、1 CPU限额；MySQL连接池3/无溢出、DB执行槽4、登录哈希并发1/每次约64MiB，继续现有限流。容器上限不是实测占用。不得用扩大共享MySQL连接或全局buffer pool、增加Swap或常驻服务解决未经定位的问题。

照明/数独只在目录/恢复/开始/完成/放弃时请求；正式扫雷初级另有由玩家点击驱动的有界揭格请求，不逐秒轮询。星级是阈值比较、成长是有限行事务。照明/数独出题、唯一解搜索和素材处理放开发机；扫雷只需服务器轻量随机布雷，不在线搜索无猜解。服务端验证/解析有尺寸和灯泡数量上限，实际耗时纳入测试。

### 12.2 PK试运行初始上限（容量门槛，不是承载承诺）

| 项目 | 建议初始值 |
| --- | --- |
| 活跃双人房间 | 4个（最多8名对局玩家） |
| 等待匹配人数 | 8人 |
| SSE连接 | 全局最多16条，账号1条；覆盖对局＋排队，不能另开无界观战流 |
| 单连接通知队列 | 16条，每条≤2KiB |
| 普通写请求体 | 4KiB；灯泡数组与DTO额外限制；论坛仍单独32KiB |
| 开始/重开频率 | 每账号建议≤10次/分钟，超过429 |
| 非法终盘提交 | 每账号建议≤30次/分钟，并对PK每房间每人设有限总次数 |
| 生命周期 | 等待房间5分钟、排队60秒、比赛10分钟、重连宽限30秒 |

`--limit-concurrency 32`会受到长响应/连接影响，16条流只是在保留余量前提下的起点，不等价于剩下16个玩家。先在现有启动参数下测HTTP/SSE共存和健康检查；若需调整全局阈值，必须有测量依据，并保留应用级PK容量拒绝，不能简单删除所有限制。超限503＋Retry-After，已进行比赛不被新连接挤占。

### 12.3 验收方法与通过门槛

先记录目标机宝塔/其他服务本底，再分阶段开启单人成长、2人/4人/8人对局、8人排队，并叠加正常登录/论坛/成长读取。对局连接维持至少30分钟，结束/重连循环再观察至少30分钟。

记录整机CPU、MemAvailable、API RSS/容器峰值、Swap换入换出、OOM、MySQL连接/锁等待、DB槽位拒绝数、请求P50/P95/P99、错误率、SSE队列/连接/断线和房间数量。测试日志不含凭据，使用专用测试库和账号。

建议上线门槛：无OOM、无持续换页；保留项目目标至少350MiB MemAvailable；API低于320MiB上限并有峰值余量；测试结束无房间/监听/线程/连接持续增长；用户结算/普通API P95目标≤500ms（不含登录密码计算），PK开始/结束事件P95目标≤1秒；额定负载非预期5xx低于1%，健康检查稳定；容量外流量可控429/503。以上是待测目标，任何一项未达标先降低PK上限/优化瓶颈，不擅自承诺满额在线。

现有预算区间不能直接相加得到“2GB一定够用”；保留350MiB余量意味着可用服务总预算更小，须按实际占用核算。没有目标机报告时，只能标记代码/本地验收完成，不能标记生产容量通过。

## 14. 发布、回滚与实施前确认

使用独立开关控制成长、外观、房间、自动匹配，默认关闭新能力；先开照明成长，再开外观，目标机负载通过后小范围开房间，最后匹配。开发一键通关只能进入独立测试身份/模式，不产生正式成长/PK结果。

部署前备份项目数据库/站点配置/旧镜像/网页；Flyway按现有维护窗口运行，考虑迁移512MiB与在线服务峰值叠加，不常驻。新迁移优先增量建表和兼容字段；旧版本无数据访问冲突时允许回退应用，不能假设数据库DDL可事务回滚。回退停用新开关、取消活跃PK、恢复匹配的前端/API版本，保留已经发放权益和存档；修复数据使用新增迁移，不修改已执行SQL。

生产新等级/外观不追溯旧客户端自报成绩、本地练习或开发通关；老游戏/成绩保持可用，新照明成长从新正式尝试开始。未来要补偿老玩家，应单独设计受控一次性赠送规则，不把旧时间当作可验证终盘。

已确认的玩法决策：最高星级、首次通关/提星一次性经验、首次达到三星有加成、星数不消费、统一账号等级和四组解锁、开始后离开继续计时、先双人房间再匹配、首版无段位/观战/成长奖励，以及扫雷初级AND照明第1关AND数独初级后才解锁PK。

仍待方案确认的数值：经验30/每星10/满星额外20、等级阈值、10星主题门槛、PK等待/重连/平局窗口、尝试/历史保留期限及试运行容量上限。题目难度阈值、数独初级题、主题样式和最终页面交互在内容/前端设计阶段确认。

HTTP契约、事务、数据模型、资源保护和验收顺序可先评审；具体前端视觉由用户后续提供后再定稿。本方案确认后按P0～P7执行，不把提出方案视为已授权立即修改整个项目。
